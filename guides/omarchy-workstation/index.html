    Keep an Omarchy workstation reproducible¶

    Omarchy sets up Arch Linux as a complete desktop. What you add on top (packages, dotfiles, a timer or two, something from the AUR) is usually done by hand and remembered by nobody. This guide keeps that layer in a recipe: a fresh Omarchy install plus sadame apply gives the same machine, and sadame drift answers "did I break my laptop?" in one command. It uses examples/12-omarchy-workstation.

    The recipe¶

    examples/12-omarchy-workstation/recipe.rb
    # A personal Arch or Omarchy workstation, applied locally:
#
#   sudo sadame apply examples/12-omarchy-workstation
#
# Packages from the official repositories, dotfiles from files/ into your
# home directory, a systemd user timer, and an AUR package through yay.
# Run `sudo sadame drift ...` now and then: exit 0 means the laptop still
# matches the recipe.
raise "this example is for Arch Linux and Omarchy, not #{platform.description}" unless platform.family == "arch"

me = vars[:user]
raise "run it with sudo, or pass --var user=NAME" if me.nil? || me.empty? || me == "root"

home = "/home/#{me}"

# Packages: only what you want on top of Arch or Omarchy.
vars[:packages].each { |name| package name }

# Dotfiles. Directories are listed so that they belong to you, not root.
["#{home}/.config", "#{home}/.config/systemd", "#{home}/.config/systemd/user", "#{home}/.local",
 "#{home}/.local/bin"].each do |path|
  directory path, owner: me, mode: "0755"
end
file "#{home}/.gitconfig", template: "gitconfig.erb", owner: me, mode: "0644"
file "#{home}/.config/starship.toml", source: "starship.toml", owner: me, mode: "0644"
file "#{home}/.local/bin/update-system", source: "update-system", owner: me, mode: "0755"

# A user timer that empties ~/Downloads of files older than 30 days. Your
# systemd instance must run even when you are logged out, so lingering is
# turned on and the instance started.
exec "enable lingering for #{me}",
     command: "loginctl enable-linger #{me}",
     creates: "/var/lib/systemd/linger/#{me}"
exec "start #{me}'s systemd instance",
     command: "systemctl start user@$(id -u #{me}).service",
     not_if: "systemctl is-active --quiet user@$(id -u #{me}).service"
exec "reload #{me}'s systemd units",
     command: "systemctl --user -M #{me}@ daemon-reload",
     action: :nothing
file "#{home}/.config/systemd/user/clean-downloads.service",
     source: "clean-downloads.service",
     owner: me,
     mode: "0644",
     notifies: [:run, "exec[reload #{me}'s systemd units]", :immediately]
file "#{home}/.config/systemd/user/clean-downloads.timer",
     source: "clean-downloads.timer",
     owner: me,
     mode: "0644",
     notifies: [:run, "exec[reload #{me}'s systemd units]", :immediately]
service "clean-downloads.timer", user: me, enable: true, state: :running

# An AUR package. yay builds as you and asks sudo for pacman, so this needs
# passwordless sudo for pacman or a recent sudo timestamp. Skipped where
# yay is not installed, such as a plain Arch container.
vars[:aur_packages].each do |name|
  exec "install #{name} from the AUR",
       command: "runuser -u #{me} -- yay -S --needed --noconfirm #{name}",
       only_if: "command -v yay",
       not_if: "pacman -Q #{name}"
end
    examples/12-omarchy-workstation/vars.rb
    # Run with sudo: SUDO_USER is the user whose home directory is managed.
{
  user: ENV["SUDO_USER"],
  git_name: "Your Name",
  git_email: "you@example.com",
  packages: ["git", "htop", "ripgrep", "fd", "bat", "starship"],
  aur_packages: ["visual-studio-code-bin"]
}

    Copy the directory somewhere you keep under version control, edit vars.rb and the files in files/ and templates/, and add your own.

    What belongs in the recipe, and what does not¶

    In the recipe Left to Omarchy
    packages you install on top of Omarchy the packages Omarchy installs
    your dotfiles: git identity, shell prompt, editor settings Omarchy's own configuration (Hyprland, Waybar, its themes)
    your scripts in ~/.local/bin Omarchy's scripts and its update mechanism
    your systemd user units and timers Omarchy's services
    AUR packages you rely on yay itself, which Omarchy ships

    The rule of thumb: manage what you would have to redo by hand after a reinstall, and leave the files Omarchy installs and updates alone. If the recipe managed them too, every Omarchy update would show up as drift, and every apply would undo the update. When you do change one of Omarchy's settings, make the change the way Omarchy's documentation describes for local changes, so its updates and your recipe do not overwrite each other, and manage only your part.

    Running sudo sadame drift ... from time to time, or from a systemd user timer, tells you when the machine has wandered from what you wrote down.

    From a fresh install to the same machine¶

    1. Install Omarchy.
    2. Clone the repository with your recipe.
    3. Install sadame (see Install).
    4. sudo sadame apply path/to/your-recipe
    5. sudo sadame drift path/to/your-recipe; exit status 0 means done.

    Common mistakes¶

    • Running without sudo, or as root directly. Without sudo, installing packages fails; as root without sudo, SUDO_USER is empty and the recipe stops. Pass --var user=NAME if you must.
    • The AUR step asking for a password. yay runs sudo pacman, and sadame cannot answer a prompt. Run sudo -v just before, or allow pacman without a password.
    • Managing Omarchy's own files. See the table above.
    • Upgrading packages with the recipe. package means "installed", not "latest"; keep updating with pacman -Syu (or update-system from the example).
